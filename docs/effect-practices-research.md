# Effect usage and error handling research

Reviewed against the declared `effect@3.22.2` dependency and the current API structure on 2026-09-22. The guidance below uses Effect v3 documentation and oRPC's official documentation. Repository observations are from the checked-out source; they describe the current implementation, not a proposed migration requirement.

**Implementation update:** The four numbered findings below describe the code before the follow-up change. In the current worktree, known Planning Center HTTP, network, and malformed-response failures become typed faults; unexpected adapter errors remain Effect defects. Plan-item preparation and commit share one resolved request credential. Request-bound provider work requires `RequestContext` and receives the request and fiber abort signals. The near-rate-limit pause now honors cancellation. Server error logs include the request ID, method, and path. `bun run ci` and `bun run build` passed after these changes.

## Assessment

Effect already has a coherent role here: `ApplicationRuntime` runs application programs through a managed runtime, request context is supplied per execution, application faults are tagged, and the oRPC adapter translates typed failures, defects, and interruptions into transport outcomes. `ManagedRuntime` is specifically intended for integrating Effect with a framework that owns the entry point, and its disposal closes managed resources. [Effect runtime guide](https://effect.website/docs/v3/runtime)

There is no general goal of “using Effect fully.” The documented architecture deliberately keeps Hono/oRPC as transport and Planning Center adapters as Promises. Rewriting every service as an Effect would add substantial churn without solving the clearest issues below. Effect's `tryPromise` is the right constructor for a Promise that may reject, provided the `catch` conversion preserves the distinction between anticipated failures and unexpected defects. [Effect creating effects](https://effect.website/docs/v3/getting-started/creating-effects), [Effect error model](https://effect.website/docs/v3/error-management/two-error-types)

## Original findings and implementation order

1. **Fix the broad error classification first.** In `packages/api/src/application/planning-center-access.ts`, `toApplicationFault` maps _every_ other `Error` to `ExternalServiceFailure`, including possible programming errors from `createServices` or code inside Promise adapters. The transport then turns that typed fault into `BAD_GATEWAY` (502). `packages/api/src/application/identity.ts` similarly maps any non-authentication error to `PersistenceFailure`. The latter can be defensible for narrowly known database operations, but the broad Planning Center catch is too imprecise. Classify known external failures at the adapter boundary, preserve their original cause for internal diagnostics, and let truly unexpected conditions remain defects. Effect v3 distinguishes typed, anticipated failures from defects, and retains defects in `Cause` even though they are outside the typed error channel. [Effect error model](https://effect.website/docs/v3/error-management/two-error-types), [Effect unexpected errors](https://effect.website/docs/v3/error-management/unexpected-errors)

2. **Resolve request access once across a two-phase write.** In `packages/api/src/transport/orpc/plan-items.ts`, create and update execute preflight and commit as separate programs, each wrapped by `withPlanningCenterAccess`. That independently reauthorizes and builds a Planning Center client before each phase. A concurrent change to the linked account or credential could leave preflight and write using different credentials or cache scopes; this is a race risk, not an observed incident. The schedule router already demonstrates the safer pattern: resolve once, then provide the same `PlanningCenterAccess` to both phases. Preserve the existing preflight interruptibility and deliberate post-write completion behavior while doing this. Effect `Context`/`Layer` are for explicit service requirements and provision; the current request-scoped service is appropriate because credentials must not be stored in a process-scoped layer. [Effect runtime and services](https://effect.website/docs/v3/runtime)

3. **Make request cancellation an explicit requirement of read operations.** `tryPlanningCenter` uses `Effect.serviceOption(RequestContext)`, so its signature reports no `RequestContext` requirement. In a call path lacking that service, it silently omits the signal and provider work may continue after the caller disconnects. Prefer a required `RequestContext` for request-bound operations, or a separately named helper for intentionally detached work. The application already passes request abort signals through reads and treats an in-flight write differently; retain that behavior. Effect interruption is represented in an `Exit`, and interruption-aware asynchronous wrappers can receive an `AbortSignal`. [Effect concurrency and interruption](https://effect.website/docs/v3/concurrency/basic-concurrency), [Effect creating effects](https://effect.website/docs/v3/getting-started/creating-effects)

4. **Keep one error translation point and strengthen diagnostics.** `executeApplicationEffect` already maps the tagged fault union to oRPC errors and gives unexpected causes an opaque 500. This follows oRPC's documented custom-error conversion pattern; oRPC also states that `message` and `data` reach clients and must exclude sensitive values. The server's `onError` hooks currently log an error but no request ID. Add request ID and operation/path context to the server-side log or span so an opaque client 500 can be matched to its cause. Also test any mixed failure/interrupt cause before changing the current `Cause.failures` mapping, because a cause can contain more than one reason. [oRPC error handling](https://orpc.dev/docs/error-handling), [Effect Cause](https://effect.website/docs/v3/data-types/cause), [Effect tracing](https://effect.website/docs/v3/observability/tracing)

5. **Use Effect resources, retries, and tracing where they own the full operation.** The Planning Center client already has bounded GET-only retries, `Retry-After` handling, per-attempt timeout, and abort-aware delay in `packages/api/src/planning-center/core-client.ts`. Moving only its sleep to `Schedule` would split one retry policy across abstractions; move retry into Effect only if the entire provider request is expressed as an Effect and its current idempotency, timeout, and cancellation semantics remain intact. For future Effect-owned resources, `acquireRelease`/`Scope` and scoped layers ensure cleanup, including interruption. For observability, `Effect.withSpan` and log annotations can tie application operations to the request ID without changing their type. [Effect retrying](https://effect.website/docs/v3/error-management/retrying), [Effect scope](https://effect.website/docs/v3/resource-management/scope), [Effect tracing](https://effect.website/docs/v3/observability/tracing), [Effect logging](https://effect.website/docs/v3/observability/logging)

## Focused verification plan

- Reproduce an unexpected exception in a Planning Center adapter and verify it becomes an opaque internal error with a server-side cause, while a known provider failure remains a typed `BAD_GATEWAY` or `TOO_MANY_REQUESTS`.
- Exercise plan-item preflight/commit with account selection changing between phases; verify both phases use the original request access and cache scope.
- Verify a request-bound read without `RequestContext` cannot type-check, and that abort stops provider work. Preserve tests showing a disconnected client does not cancel an already-started scheduling mutation or skip its audit.
- Verify an internal error log has the request ID and excludes credentials and full request headers.

## Integration option, not a prerequisite

oRPC documents an experimental Effect integration, including Effect-aware handlers and a wrapper hook for application-level error handling. It could reduce hand-written execution adapters later, but adopting it would be a separate dependency and migration decision. The current explicit boundary is compatible with oRPC's documented custom-error conversion and keeps the contracts browser-safe. [oRPC Effect integration](https://orpc.dev/docs/integrations/effect), [oRPC error handling](https://orpc.dev/docs/error-handling)
