# Planning Center scheduling notifications via the public API

Research date: September 24, 2026. Research only; no Planning Center records were changed and no email was sent.

## Answer

**PCOBooster cannot currently trigger Planning Center's initial scheduling email through a supported public API.** A Planning Center maintainer answered this exact question in June 2026: the Accept/Decline buttons are added when Services sends the message and are not part of a rendered email template; there is no supported API route for sending that scheduling email. The public [`PlanPerson` API](https://api.planningcenteronline.com/docs/apps/services/versions/2018-11-01/vertices/plan_person) allows creating a plan assignment and setting its prepared notification state, but lists no send action. Sources: [Planning Center developer answer](https://github.com/planningcenter/developers/issues/1475#issuecomment-4615789658), [PlanPerson API](https://api.planningcenteronline.com/docs/apps/services/versions/2018-11-01/vertices/plan_person).

The distinction matters: a **prepared notification** is an unsent, penciled-in assignment, not a queued email that the API will automatically deliver. Planning Center says an unconfirmed scheduled viewer in this state cannot see the plan or schedule until the notification is sent. Disabling the prepared state makes the assignment visible without sending any email. Source: [Send scheduling emails](https://help.planningcenter.com/en/142892-send-scheduling-emails.html).

## Supported paths

| Path | What it can do | Limitation |
| --- | --- | --- |
| Send initial scheduling email in Services | A scheduler can send to a person, team, whole plan, or multiple plans in matrix view. The native email includes times, plan link, and Accept/Decline for unconfirmed people. [Planning Center guide](https://help.planningcenter.com/en/142892-send-scheduling-emails.html) | Requires a person to complete the send in Planning Center. The public API does not expose the send action. [Developer answer](https://github.com/planningcenter/developers/issues/1475#issuecomment-4615789658) |
| Configure automatic **reminder** emails | Services sends reminders at 10 a.m. local time, 0–7 days before a plan time. Unconfirmed recipients get Accept/Decline. A reminder sent before the initial scheduling email clears the prepared state and lets the person access/respond to the plan. [Reminder guide](https://help.planningcenter.com/en/142894-set-up-reminder-emails.html) | This is a delayed reminder, not a send-now scheduling request. It applies by team and plan time, only to confirmed/unconfirmed people, and cannot target individual positions separately. [Reminder guide](https://help.planningcenter.com/en/142894-set-up-reminder-emails.html) |
| Set reminder configuration via the public API | `PlanTime.team_reminders` is documented as a map from team ID to a day offset 0–7 and is assignable on PlanTime create/update. [PlanTime API](https://api.planningcenteronline.com/docs/apps/services/versions/2018-11-01/vertices/plan_time) | The documentation labels its type `array` while describing a hash. The exact accepted JSON shape and behavior for already scheduled people need a controlled test before relying on this integration. This API setting configures the later native reminder; it does not send immediately. [PlanTime API](https://api.planningcenteronline.com/docs/apps/services/versions/2018-11-01/vertices/plan_time), [Reminder guide](https://help.planningcenter.com/en/142894-set-up-reminder-emails.html) |
| Send PCOBooster's own email | A separate mail service could tell the person that an assignment was made and link to the plan. Setting `prepare_notification=false` on `PlanPerson` can make the schedule visible without a native scheduling email. [PlanPerson API](https://api.planningcenteronline.com/docs/apps/services/versions/2018-11-01/vertices/plan_person), [Planning Center guide](https://help.planningcenter.com/en/142892-send-scheduling-emails.html) | This would be a PCOBooster communication flow, not Planning Center's initial scheduling email. The template render endpoint fills person details but does not add native Accept/Decline controls or send the email. [EmailTemplate API](https://api.planningcenteronline.com/docs/apps/services/versions/2018-11-01/vertices/email_template), [Developer answer](https://github.com/planningcenter/developers/issues/1475#issuecomment-4615789658) |

Planning Center's developer answer also points to automatic reminders as the supported way to automate an email with Accept/Decline controls. [Developer follow-up](https://github.com/planningcenter/developers/issues/1475#issuecomment-4623410261).

## Current PCOBooster behavior

The current assignment create call submits `status: "U"`, person ID, team ID, and position name. It omits `prepare_notification` and makes no send request. The resulting prepared state should be read back; Planning Center documents a team-level default for it. The app cannot claim that creating the assignment delivered an email. Sources: [people service](../../packages/api/src/planning-center/services/people-service.ts), [team settings guide](https://help.planningcenter.com/en/140131-manage-team-settings.html).

The app already reads `team_reminders` from PlanTime into its `teamReminders` model, but its create/update PlanTime inputs do not write that attribute. Supporting API-configured reminders would require an explicit product and transport change, followed by a controlled Planning Center test. Sources: [plan-time module](../../packages/api/src/modules/planning-center/plan-times.ts), [plan-time schema](../../packages/contracts/src/plan-time-schemas.ts).

## Recommendation for PCOBooster

For the existing scheduling workflow, show which assignments still have prepared notifications and link directly to the matching Planning Center plan, where the scheduler can send the native email. `PlanPerson` exposes `prepare_notification`, `notification_prepared_at`, and `notification_sent_at` for this distinction. Do not label a person as notified merely because their assignment was created or the prepared flag was cleared. Sources: [PlanPerson API](https://api.planningcenteronline.com/docs/apps/services/versions/2018-11-01/vertices/plan_person), [Planning Center guide](https://help.planningcenter.com/en/142892-send-scheduling-emails.html).

If a delayed native message is acceptable, investigate `team_reminders` as a separate product option. It could let users schedule in PCOBooster and have Planning Center send a later reminder with Accept/Decline, but it will not fully replace an immediate scheduling email. A controlled test should verify exact write shape, scheduled delivery, prepared-state clearing, and how same-day/past-10-a.m. timing behaves. Sources: [PlanTime API](https://api.planningcenteronline.com/docs/apps/services/versions/2018-11-01/vertices/plan_time), [Reminder guide](https://help.planningcenter.com/en/142894-set-up-reminder-emails.html).

For a send-now experience entirely initiated in PCOBooster, an inference from the documented access rules is that the app could deliver its own email with a Planning Center plan link, then let the recipient respond in Planning Center after the prepared state is cleared. This needs a recipient-facing test before treating it as a finished workflow. A PCOBooster-owned Accept/Decline interaction would be a larger separate project: the public Schedule API has accept/decline actions, but authorization and recipient identity would need investigation. Neither path reproduces Planning Center's native scheduling email or its notification history. Rendering a Planning Center template does not supply native response links or send the email. Sources: [Planning Center guide](https://help.planningcenter.com/en/142892-send-scheduling-emails.html), [EmailTemplate API](https://api.planningcenteronline.com/docs/apps/services/versions/2018-11-01/vertices/email_template), [Schedule accept/decline API](https://api.planningcenteronline.com/docs/apps/services/versions/2018-11-01/vertices/schedule), [developer answer](https://github.com/planningcenter/developers/issues/1475#issuecomment-4615789658).

**Confidence:** High on the absence of a supported native send action and on the documented reminder behavior; medium on programmatic reminder configuration until a write is tested against a disposable plan. The public documentation and developer answer are current as of the research date. No authenticated endpoint test was performed.

## Follow-up: can PCOBooster reuse the native Accept/Decline links?

**The public API does not provide a documented way to generate or retrieve those email response links.** A developer asked Planning Center specifically whether a link could be added to a button in an externally sent email. Planning Center answered that Services appends the buttons when it sends the scheduling message and that sending such a message from the API is unsupported. The [`EmailTemplate.render` action](https://api.planningcenteronline.com/docs/apps/services/versions/2018-11-01/vertices/email_template) only fills in person details; it does not return the native response controls. Sources: [the exact developer question and Planning Center answer](https://github.com/planningcenter/developers/issues/1475), [EmailTemplate API](https://api.planningcenteronline.com/docs/apps/services/versions/2018-11-01/vertices/email_template).

Planning Center documents different behavior depending on the email: a single-request **Accept** sends the response automatically, while **Decline** opens Services to collect a reason and possibly a replacement; a combined email instead has **Respond To Requests**, which opens Services for individual choices. The [recipient guide](https://help.planningcenter.com/en/142893-respond-to-scheduling-emails.html) describes behavior but does not publish the underlying URL structure, how a link is authorized, or whether it expires. We did not inspect a real recipient email, so the literal URLs and any token, authentication, or expiry rules remain unknown. A URL copied from one message would not establish a reusable way to create a valid link for another person or assignment. Sources: [Respond to scheduling emails](https://help.planningcenter.com/en/142893-respond-to-scheduling-emails.html), [developer answer](https://github.com/planningcenter/developers/issues/1475#issuecomment-4615789658).

The [public Schedule API](https://api.planningcenteronline.com/docs/apps/services/versions/2018-11-01/vertices/schedule) has `POST` accept and decline **API actions** for an identified person's schedule. Those endpoints are not documented as the links embedded in the email; using them would mean building a PCOBooster-owned recipient response flow, with its own identity and authorization checks. If the assignment is visible to the recipient (for example, after its prepared state is cleared), a PCOBooster email could instead have a **Respond in Planning Center** button linking to [My Schedule](https://help.planningcenter.com/en/143027-my-schedule.html), where the recipient chooses a response. Labeling separate links **Accept** and **Decline** would promise direct actions that the public link documentation does not establish. Source for prepared-state visibility: [Send scheduling emails](https://help.planningcenter.com/en/142892-send-scheduling-emails.html).

## Follow-up: shorten the handoff for a scheduler to send native emails

The public [Plan API](https://api.planningcenteronline.com/docs/apps/services/versions/2018-11-01/vertices/plan) supplies a `planning_center_url` for each plan, which PCOBooster already uses for **Open in Planning Center** ([catalog mapping](../../packages/api/src/modules/planning-center/get-plans.ts), [dashboard link](../../apps/web/src/components/dashboard-page.tsx)). This is the confirmed plan-level destination for a native-send handoff. From that plan, Planning Center's [send guide](https://help.planningcenter.com/en/142892-send-scheduling-emails.html) directs the scheduler to **Teams**, then one of the following controls:

| Handoff in Planning Center | Best fit | Remaining action |
| --- | --- | --- |
| Envelope beside a person with an unsent prepared notification | One volunteer | Review the email popup and select **Send**. The envelope only appears while that person's prepared notification is unsent. [Send guide](https://help.planningcenter.com/en/142892-send-scheduling-emails.html) |
| **Send** above a team's scheduled positions | One team | Review the email popup and select **Send**. [Send guide](https://help.planningcenter.com/en/142892-send-scheduling-emails.html) |
| Envelope at the top right of a plan | All eligible scheduled people for that plan | Choose recipients (including **Only people with Prepared Notifications**), select **Next**, review the message, then **Send**. [Communication guide](https://help.planningcenter.com/en/142889-communicate-with-your-teams.html) |
| Envelope at the top right of a matrix | Requests across several plans | Review recipients and send one consolidated email per person covering the loaded plans. This is useful for a scheduler working weeks ahead, but would require a separate handoff to the right matrix. [Matrix guide](https://help.planningcenter.com/en/139475-use-the-matrix-to-schedule.html), [email-template guide](https://help.planningcenter.com/en/142895-create-email-templates.html) |

These are native Planning Center scheduling emails with its own response controls. A scheduler's permissions still govern the recipients: Planning Center says schedulers can email the teams they lead; broader plan-wide sends must respect that limit. [Schedule your teams](https://help.planningcenter.com/en/142868-schedule-your-teams.html), [communication guide](https://help.planningcenter.com/en/142889-communicate-with-your-teams.html).

**Direct link status:** Planning Center documents the plan URL and the controls on the Teams tab, but its public help and API docs do not publish a URL parameter or route that opens the Teams tab, selects prepared recipients, or opens the email composer. We therefore cannot promise a one-click-from-PCOBooster native send. A read-only check in a signed-in browser could determine whether the Teams tab has a stable, shareable URL for this account; any observed route would be an uncontracted UI link and should be tested from a fresh tab and on mobile before use. We should not construct a guessed composer URL or automatically click **Send**. [Plan API](https://api.planningcenteronline.com/docs/apps/services/versions/2018-11-01/vertices/plan), [send guide](https://help.planningcenter.com/en/142892-send-scheduling-emails.html).

**Recommended near-term flow:** In PCOBooster, show the count and names of still-prepared assignments, offer **Send scheduling emails in Planning Center** using the existing `planning_center_url`, and tell the scheduler to open **Teams** and use the plan envelope with **Only people with Prepared Notifications**. Refresh the plan afterward and use `notification_sent_at` / `prepare_notification` to distinguish sent from still prepared; do not treat the handoff click as proof of delivery. [PlanPerson API](https://api.planningcenteronline.com/docs/apps/services/versions/2018-11-01/vertices/plan_person), [communication guide](https://help.planningcenter.com/en/142889-communicate-with-your-teams.html). If an org schedules several plans at once, offer a matrix handoff as a later workflow, after confirming a reliable matrix destination. Planning Center [supports schedule email templates](https://help.planningcenter.com/en/142895-create-email-templates.html) for the native composer, which can reduce repetitive message editing but not eliminate the final human send.

## Follow-up: per-person sent status

Yes. Each `PlanPerson` represents a person's assignment to a plan and exposes `notification_sent_at`, `notification_prepared_at`, `prepare_notification`, and `notification_sender_name`. The plan's `team_members` endpoint lists these resources, so one plan-level read can inspect the assignment records rather than fetching each person separately. [PlanPerson API](https://api.planningcenteronline.com/docs/apps/services/versions/2018-11-01/vertices/plan_person)

| Assignment fields | Safe interpretation |
| --- | --- |
| `notification_sent_at` is present | Planning Center records a notification send for this assignment at that time. This is a sent record, not proof of inbox delivery or reading. |
| `prepare_notification` is `true` | The assignment has a prepared notification awaiting the native send flow. Planning Center describes this as a penciled-in state. |
| `prepare_notification` is `false` and `notification_sent_at` is absent | Do **not** label it sent: a scheduler can clear the prepared state without sending email. |

Sources: [PlanPerson fields](https://api.planningcenteronline.com/docs/apps/services/versions/2018-11-01/vertices/plan_person), [prepared notification behavior](https://help.planningcenter.com/en/142892-send-scheduling-emails.html). The public field documentation does not specify how repeated scheduling emails or reminders update `notification_sent_at`; validate those transitions before turning the fields into a complete communication history. PCOBooster already fetches plan `team_members` in its [people service](../../packages/api/src/planning-center/services/people-service.ts), but its [roster shape](../../packages/api/src/modules/planning-center/plan-scheduling-context.ts) does not expose these notification fields. No authenticated live response was checked in this research session because this checkout has no Planning Center PAT configured.
