# API architecture

The product API is a contract-first oRPC service served by Hono inside an Alchemy Effect-native Cloudflare Worker (`apps/server/src/worker.ts`). Effect owns application execution below the transport boundary. Better Auth remains an ordinary HTTP handler because it defines its own protocol and routes.

## Package boundaries

- `packages/contracts` contains browser-safe oRPC contracts, transport DTO schemas, and safe error payload schemas. It must not import database, auth, Hono, framework, or Effect modules.
- `packages/planning-center-models` contains shared Planning Center data shapes plus pure calendar and scheduling rules. It is browser-safe and framework-independent.
- `packages/presentation-mode` contains the server-side presentation-mode guard, seed, and cache namespace shared by the API and the web build, which inlines the namespace.
- `packages/api` contains server-side application programs, typed faults, explicit feature modules, Better Auth and database integration, Planning Center adapters, and the oRPC implementation of the contracts.
- `apps/server` is the API Worker. It reads its settings with `Config` at startup, binds D1, builds the server dependencies once per isolate, mounts Better Auth and the oRPC handlers, supplies raw request context, and configures cross-origin and response-header behavior.
- `apps/web` consumes `packages/contracts` through the oRPC client and owns browser caches, hydration, navigation, and presentation helpers under `src/lib`. It must not import server-side modules from `packages/api`.

## Request flow

```text
apps/web
  -> oRPC contract client
  -> apps/server /api/rpc
  -> packages/api transport adapter
  -> Effect application program
  -> packages/api feature module
  -> Planning Center or database adapter
```

The Worker builds `ServerDependencies` (`packages/api/src/server.ts`: the typed `ServerConfig`, the Drizzle database, Better Auth, and the feature flag client) once per isolate. The Worker's construction phase acquires the D1 and Cloudflare Flagship bindings, as `Cloudflare.D1.QueryDatabase` and `Cloudflare.Flagship.ReadFlags`, and passes the raw bindings in. Programs evaluate flags per request with `featureFlags.isEnabled(name, subject)`, never from configuration; see [Feature flags](environment.md#feature-flags). The oRPC context carries them, and every execution provides them to the program as the `Server` service; `packages/api` never reads `process.env` or `cloudflare:workers`. One process-scoped `ApplicationRuntime` owns shared Effect layers. Every execution also provides a new `RequestContext`, including a request ID, cloned headers, method, URL, user-agent metadata, and abort signal. Credentials and other identity-sensitive values belong in request-scoped services; they must not be captured by a process-scoped layer or implicit async context. Planning Center clients bind one explicit credential to both their Authorization header and cache scope for their entire lifetime. A [demo session](demo.md) resolves to the demo credential through a read-only client that rejects writes before they leave the process, and always presents people with fictional details.

Application programs fail with tagged application faults rather than HTTP statuses. The oRPC adapter maps each expected fault to a declared contract error once. Planning Center HTTP, network, and malformed-response errors are classified at the provider boundary; unexpected adapter errors remain Effect defects. Defects and persistence failures are returned as opaque internal errors, with their original cause retained only for server-side logging.

All oRPC and OpenAPI responses are marked `Cache-Control: private, no-store` at the Hono boundary. oRPC's response-header plugin preserves procedure-specific headers such as account-selection cookies.

## Planning Center adapters

The Planning Center client (`packages/api/src/planning-center/core-client.ts`), the services under `planning-center/services/`, and the feature modules under `modules/planning-center/` return Effects end to end. Their typed failure channel is `PlanningCenterError`: `PlanningCenterApiError` (an error status or unusable response), `PlanningCenterNetworkError` (fetch, body stream, or attempt timeout), `PlanningCenterReadOnlyError` (a blocked demo write), `PlanningCenterRateLimitError` (the credential's rate budget is spent for longer than the wait cap, so the request was not sent), and `PlanningCenterSubrequestLimitError` (Cloudflare refused the fetch with "Too many subrequests", or the procedure's request budget is spent). Application programs compose them directly and translate that channel once with `withPlanningCenterFaults`, which maps read-only writes to `Forbidden`, 429 responses and pacing rejections to `RateLimited` (with `retryAfterSeconds`), and subrequest limits and other provider failures to `ExternalServiceFailure`; anything else stays a defect. Feature modules that fall back to empty data after a failure should let `PlanningCenterSubrequestLimitError` and `PlanningCenterRateLimitError` through, or return partial data marked as such, instead of swallowing them.

- **HTTP.** The client sends through an `effect/unstable/http` `HttpClient`. The process-scoped `ApplicationRuntime` provides `FetchHttpClient.layer`, `resolvePlanningCenterAccess` reads that client from context, and the request's services bind it together with the request credential for their lifetime. Tests pass an `HttpClient` over a scripted `fetch` (`testing/http-client.ts`).
- **Retries and timeouts.** Only idempotent reads (GET and HEAD) retry, on a `Schedule` of at most two retries: 408, 429, 500, and 502 to 504 responses and attempt timeouts qualify; 429 waits for `Retry-After`, other responses back off 500 ms per retry, and timeouts 300 ms. A 429 whose `Retry-After` is longer than 5 seconds is not retried: the read fails at once with the 429 (`RateLimited` with `retryAfterSeconds`) so the browser can retry instead of holding the request open. A subrequest limit is never retried. Each attempt (pacing wait, request, and error body) has a 15 second Effect timeout, and the JSON body read uses what remains of that budget.
- **Pacing.** `PlanningCenterRatePacer` (`planning-center/rate-pacer.ts`) keeps one window per credential (cache scope) in the isolate, learned from each response's `X-PCO-API-Request-Rate-Limit`, `-Count`, and `-Period` headers; it never assumes 100 per 20 seconds. The process-scoped `ApplicationRuntime` provides one pacer as the `PlanningCenterPacing` service, so every procedure for the same credential in the isolate shares it. Until half the reported limit is used (counting requests still in flight), reads go straight out. After that, each read takes the next slot, spaced `time left in the window / requests left`, so the remaining budget is spread across the window before sending rather than paused after the response. A 429 blocks the credential until its `Retry-After`. A read whose slot is more than 5 seconds away fails with `PlanningCenterRateLimitError` without being sent. Writes are counted but never delayed or rejected by the pacer, keep their no-retry rule, and still follow the provider-write boundary below. The pacer cannot see other isolates, tabs, or devices using the same Planning Center user; only a Durable Object per user could.
- **Request accounting.** A root oRPC middleware (`transport/orpc/implementation.ts`, `transport/orpc/planning-center-accounting.ts`) creates one `PlanningCenterRequestAccounting` per procedure call and puts it in the oRPC context; `executeApplicationEffect` provides it to every execution in that procedure as the `PlanningCenterAccounting` service. The client counts each request it sends (retries included), paced requests and their wait, 429s, pacing rejections, and subrequest-limit hits. Programs read the count with `currentPlanningCenterRequestCount` (or `accounting.requestCount` and `remainingBudget`) to stop early and return partial data. `PLANNING_CENTER_REQUEST_BUDGET` sets a per-procedure cap after which the client fails with `PlanningCenterSubrequestLimitError` (`source: "budget"`) before Cloudflare would refuse the fetch. It is off by default; the count covers Planning Center fetches only, not D1, KV, or service-binding calls, so a budget such as 40 leaves room for those within Workers Free's 50. After Cloudflare refuses one fetch, later requests in the same procedure fail at once without being sent. Code outside a procedure (scripts, most unit tests) has no accounting and no pacer, so its requests are neither counted nor paced.
- **Logs.** Every pacing wait, pacing rejection, and 429 is logged at `info` with the endpoint (path and query parameter names only, never values, tokens, or bodies), method, attempt, wait or `Retry-After`, and the rate-limit headers. Cloudflare "Too many subrequests" refusals log at `warn`. Each procedure that touched Planning Center logs one `info` line, "Planning Center procedure summary", with the procedure path (for example `people.list`), request ID, duration, outcome, and its counts. The client and the summary take an injectable `PlanningCenterLogger`; they default to the pino module loggers.
- **Caches.** `cachedRead` (`planning-center/services/cached-read.ts`) adapts an Effect load to the shared `PlanningCenterReadCache`. The load is built only on a miss and runs in its own fiber, so each caller waits independently.

Cancellation is Effect interruption. A read runs in the request's fiber, which the transport interrupts when the Fetch request aborts; interrupting a Planning Center call aborts its in-flight fetch, pacing wait (releasing its slot), or pagination. Shared cache loads keep per-caller waiters: one disconnected caller does not cancel another, but the load is interrupted and its result is not cached when no callers remain. Optional reads that fall back after a failure (the organization time zone, blockouts, candidate history) still stop when interrupted. At the provider-write boundary, the application checks the request signal once more (`ensureRequestIsOpen`); writes run without request-driven interruption, so after a write starts, execution waits for the provider result and required invalidation or audit work instead of reporting a cancellation while a hidden write continues.

## Migration invariants

Each migration layer owns a complete vertical slice: contract, application program, oRPC procedure, web caller, tests, and deletion of the replaced REST route. Do not leave a second business implementation behind as a compatibility path. Better Auth routes, liveness health checks, and the OpenAPI reference are the only intentional non-oRPC HTTP surfaces after cutover.
