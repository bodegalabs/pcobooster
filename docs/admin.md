# Admin app

`apps/admin` is a private TanStack Start app for account activity. It lives at `https://admin.pcobooster.com` and never appears in the product UI, demos, or presentation mode.

## Access

Cloudflare Access is the only gate. The admin app has no sign-in of its own and does not use the product session: its server functions read the product's D1 database through the admin Worker's own `DB` binding, and the public API (`pcobooster.com/api`) has no admin procedures, so nothing outside the admin Worker can read admin data.

- **Production:** `alchemy.run.ts` gives the admin Worker (`admin.pcobooster.com` and its workers.dev URL) a dedicated Access application admitting `PCOBOOSTER_ADMIN_EMAILS`, with a 24-hour session. The production deploy token carries **Access: Apps and Policies Write** for it (`alchemy.ci.ts`).
- **Staging and previews:** admin has no public URL; it is served at `/admin` through the product Worker, which sits behind that stage's own Access application admitting the same addresses (see [CI/CD](ci-cd.md#staging)).
- **Local:** `bun run dev` has no Access; admin is open on `127.0.0.1`.

Every read also checks the Access login itself (`src/server/access-identity.ts`). Deployed stages give the admin Worker `ACCESS_TEAM_DOMAIN`, and its server functions render the not-found page, never data, unless the request carries an Access token (the `Cf-Access-Jwt-Assertion` header or the `CF_Authorization` cookie) signed by that team's keys, issued by the team, and naming a person. Service tokens name no person, so CI's deploy check cannot read admin data. This keeps admin closed even if its Access application were ever missing or failed to deploy, as happened once when the production token lacked the right permission. The index page shows the verified email.

Add or remove people in `PCOBOOSTER_ADMIN_EMAILS` (comma-separated); the next deploy of each stage updates its policy.

Every Worker response carries `X-Robots-Tag: noindex, nofollow`, `Referrer-Policy: no-referrer`, and `Cache-Control: private, no-store` (`src/start.ts`).

## PostHog

Each user page links to the matching PostHog person. The product identifies PostHog persons by the same Better Auth user ID, and the API sets email, name, and church on sign-in, so the admin page and PostHog describe the same people. See [analytics](analytics.md#server-activity-and-person-profiles).

## Code layout

- `src/routes/`: file routes. Each page's `loader` calls a server function, so pages are fully server-rendered and client navigations fetch through `/admin/_serverFn/*` (or `/_serverFn/*` in production). `src/routeTree.gen.ts` is generated by Vite and committed; `vite dev`/`vite build` regenerate it after route changes.
- `src/server/admin.functions.ts`: server functions. They read the `DB` binding from `cloudflare:workers` (typed in `src/worker-env.d.ts`) and call the account-activity queries in `@pcobooster/api/modules/admin` with the same Drizzle client the API uses; responses follow the schemas in `@pcobooster/contracts/admin`. An unknown user renders the not-found page.
- `src/start.ts`: request middleware for CSRF protection on server functions and the private response headers.

## Development and deployment

`bun run dev` serves the admin app through `http://127.0.0.1:3001/admin`, and its Vite dev server also listens on 3003. Alchemy binds the same local D1 database the API uses, so admin shows local accounts.

Alchemy deploys a dedicated admin Worker (`Cloudflare.Website.Vite`) bound to its stage's D1 database. Production serves it at `admin.pcobooster.com`. Staging and each preview serve it through the product's `/admin` route; there the admin Worker has no public workers.dev endpoint.

The mount path is Vite's `base`, from `ADMIN_BASE_PATH`: `/admin` for local and preview stages and empty for production. Without the variable, the dev server defaults to `/admin` and builds default to the root. The router basepath, server-function URLs, and uploaded asset paths all follow `base`. The product forwards `/admin` and `/admin/*` unchanged, and Start redirects the bare mount path to its canonical `/admin/`. Alchemy's memo hashes files but not the environment, so the stage stamp in `cloudflare-build-inputs.json` is part of the rebuild key.

`bun run --cwd apps/admin build` is a standalone validation build that CI runs in `cloudflare-build`. It uses `@cloudflare/vite-plugin` with inline Worker config. Under Alchemy that plugin stands down (`ALCHEMY_CLOUDFLARE_VITE_INJECTED`), and Alchemy builds and uploads the Worker itself.
